# Деплой WildFinance на VPS + автодеплой из GitHub

Как это работает: ты делаешь `git push` в ветку `main` → GitHub Actions прогоняет тесты →
если они зелёные, заливает код на сервер и перезапускает бота в Docker →
через 25 секунд проверяет, что бот жив. Если бот падает, автоматически
возвращается предыдущая версия, а в GitHub деплой помечается красным.

```
push в main ─► тесты ─► rsync кода на VPS ─► docker compose build/up ─► проверка ─► ✅ / ↩️ откат
```

Секреты (`.env`) и база (`data/users.db`) живут **только на сервере** и деплоем не трогаются.

---

## Шаг 0. Важно до начала

- **Одновременно может работать только один экземпляр бота с одним токеном.**
  Как только бот запустится на сервере, останови его у себя на компьютере, иначе оба
  будут ругаться `TelegramConflictError`. Для разработки заведи в @BotFather отдельного
  тестового бота со своим токеном.
- Перевыпусти токен бота (`/revoke` в @BotFather), если ещё не сделал: старый засветился в отчёте.

## Шаги 1–2. Подготовка сервера (один раз)

С компьютера, из папки `solution` (в `.env` уже должен быть **новый** токен):

```powershell
scp deploy\server_setup.sh deploy\migrate_from_zip.sh .env root@IP_СЕРВЕРА:/root/
ssh root@IP_СЕРВЕРА
```

На сервере:

```bash
bash /root/server_setup.sh
```

Скрипт поставит Docker, создаст пользователя `deploy` и папку `/opt/wildfinance`, перенесёт туда `.env`,
сгенерирует ключ для GitHub Actions и в конце **выведет все значения для секретов GitHub**
(шаг 4). Файрвол не трогается: включить его можно командой `ENABLE_UFW=1 bash /root/server_setup.sh`.

База пользователей: если бот уже работал на этом сервере, её перенесёт скрипт из шага 2½
(на сервере она свежее, чем твоя локальная). Если это новый сервер, скопируй локальную:
`scp users.db root@IP_СЕРВЕРА:/opt/wildfinance/data/users.db`.

```bash
# на сервере
chown -R deploy:deploy /opt/wildfinance && chmod 600 /opt/wildfinance/.env
```

## Шаг 2½. Переезд со старого деплоя (deploy.zip)

Если бот уже крутится на этом сервере из `deploy.zip`, его нужно аккуратно заменить:
сохранить базу пользователей и остановить старую версию, иначе будет два бота на одном токене.

Скрипт `migrate_from_zip.sh` уже загружен на сервер на шаге 1–2.

На сервере сначала **пробный прогон**: он только найдёт старого бота и сделает бэкап базы,
ничего не останавливая:

```bash
bash /root/migrate_from_zip.sh
```

Скрипт покажет, как был запущен старый бот (Docker / systemd / screen), куда сохранил
`users.db`, и положит самую свежую базу в `/opt/wildfinance/data/`.
Если всё выглядит правильно, **прямо перед первым деплоем** (шаг 5) выполни:

```bash
bash /root/migrate_from_zip.sh --stop
```

Старый контейнер не удаляется, только останавливается: вернуть его можно командой `docker start <имя>`.
Когда новый бот проработает пару дней, старую папку с распакованным zip и сам `deploy.zip`
на сервере лучше удалить: **внутри архива лежит старый `.env` с токенами**.

> Если ты уже сделал `/revoke` токена, старый бот сам перестал работать. Базу это не трогает,
> скрипт всё равно её найдёт.

## Шаг 3. Репозиторий на GitHub

1. Создай на github.com **приватный** репозиторий (без README).
2. В папке `solution` на компьютере положи workflow на место (из-за ограничений доступа
   я не смог сам записать файл в `.github`):

```powershell
mkdir .github\workflows -Force
move deploy\github-actions-deploy.yml .github\workflows\deploy.yml
```

3. Закоммить и отправь код:

```powershell
git log --all --oneline -- .env      # должно быть ПУСТО: .env никогда не коммитился
git add -A
git commit -m "P0: пример отчёта, ABC, /compare, автооплата, автодеплой"
git branch -M main
git remote add origin https://github.com/<твой-логин>/<репо>.git
git push -u origin main
```

> Если `git log -- .env` что-то показал, значит `.env` попадал в историю.
> Не пушь такой репозиторий: напиши мне, почистим историю.

## Шаг 4. Секреты в GitHub

Репозиторий → **Settings → Secrets and variables → Actions → New repository secret**:

| Секрет | Что вписать |
|---|---|
| `SSH_HOST` | IP сервера |
| `SSH_USER` | `deploy` |
| `SSH_PORT` | порт SSH (можно не создавать, если 22) |
| `SSH_PRIVATE_KEY` | приватный ключ, который вывел `server_setup.sh`, включая строки `-----BEGIN/END-----` |
| `SSH_KNOWN_HOSTS` | строки, которые вывел `server_setup.sh` (защита от подмены сервера) |

Все значения печатает `server_setup.sh`. После того как вставишь ключ в GitHub, удали его с сервера:
`rm /root/github_deploy_key`.

Секреты бота (`BOT_TOKEN`, ключи AI, ЮKassa) в GitHub **не нужны**: они лежат в `.env` на сервере.

## Шаг 5. Первый деплой

Вкладка **Actions** → workflow «Test & Deploy» → **Run workflow** (или просто сделай push).
Зелёная галочка означает, что бот работает на сервере.

Дальше любой `git push` в `main` деплоится сам.

## Полезные команды на сервере

```bash
cd /opt/wildfinance
docker compose logs -f --tail 100   # логи в реальном времени
docker compose restart              # перезапуск (например, после правки .env)
docker compose ps                   # статус
cp data/users.db ~/users_$(date +%F).db   # бэкап базы
```

После изменения `.env` на сервере нужен `docker compose up -d` (перечитает переменные).

## Если деплой красный

- **Упали тесты**: деплой не запускался, бот на сервере работает на старой версии. Смотри лог шага «Тесты».
- **Упал «Сборка и перезапуск»**: в логе будут последние строки логов бота. Версия уже откатилась.
- **`Permission denied (publickey)`**: проверь `SSH_PRIVATE_KEY` и что публичный ключ лежит в
  `/home/deploy/.ssh/authorized_keys`.
- **`Host key verification failed`**: пересоздай `SSH_KNOWN_HOSTS` через `ssh-keyscan`.
